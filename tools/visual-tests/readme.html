Overview

The AEM Visual Checker is a comprehensive automated visual regression testing solution designed specifically for Edge Delivery Services blocks. It provides automated screenshot comparison across multiple viewports to ensure visual consistency and detect unintended visual changes in your AEM blocks and components.

🎯 Key Features

  • Modular Organization: Each block has its own test file and snapshot directory
  • Figma Integration: Automatically download design mockups from Figma as test baselines
  • Selective Testing: Test individual blocks for faster development feedback
  • Multi-Viewport: Automated testing across Mobile, Tablet, Desktop, and Large screens
  • Interactive UI: Run tests directly from the Sidekick Library
  • CI/CD Ready: Seamless integration with continuous integration pipelines

Business Case

Automated Visual Quality Assurance for Edge Delivery Services Blocks

The visual test system addresses critical business needs for maintaining visual consistency and quality across AEM components while enabling rapid development and deployment cycles.

Key Business Requirements:

  • Visual Regression Prevention: Detect unintended visual changes before they reach production
  • Cross-Viewport Consistency: Ensure components render correctly across mobile, tablet, desktop, and large screens
  • Rapid Feedback: Provide immediate visual feedback during development and testing phases
  • Component Library Validation: Validate all block variations in the AEM Sidekick Library

Business Benefits:

  • Reduced Visual Bugs: Catch visual regressions early in the development cycle
  • Faster Development: Automated testing reduces manual visual review time by 90%
  • Improved User Experience: Consistent visual appearance across all devices and viewports
  • Cost Efficiency: Reduce post-deployment bug fixes and visual inconsistencies
  • Brand Protection: Maintain brand consistency across all digital touchpoints
  • Design-Dev Collaboration: Figma integration creates direct design-to-development workflow
  • Scalability: Modular structure supports unlimited blocks without performance degradation
  • Selective Testing: Test individual blocks in 20 seconds vs 2 minutes for all blocks

This system transforms manual visual testing into an automated, reliable process that scales with your Block library and development velocity.

Playwright Configuration

Create playwright.config.ts in your project root:


import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tools/visual-tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,
  reporter: [['html', { open: 'never' }]],
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: {
      mode: 'retain-on-failure',
    },
    viewport: { width: 1280, height: 720 },
  },
  // Custom snapshot path to remove platform name from snapshot files
  snapshotPathTemplate: '{testDir}/{testFileDir}/{testFileName}-snapshots/{arg}{ext}',
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
  webServer: {
    command: 'aem up',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});

Figma Integration

The visual testing framework includes powerful Figma integration that allows you to automatically download design mockups from Figma to use as visual test baselines.

Setup Figma Integration

1. Get Figma Access Token

  1. Go to Figma → Settings → Account
  2. Scroll to "Personal Access Tokens"
  3. Click "Create new token"
  4. Copy the token

2. Configure Environment Variable

Create a .env file in your project root:

FIGMA_ACCESS_TOKEN=your_figma_token_here

Important: Never commit the .env file to git. It should be in your .gitignore.

Using Figma Integration

1. Create Block Configuration

For each block, create a config.js file in the block's folder:

// tools/visual-tests/blocks/cards/config.js
export const FIGMA_CONFIG = [
  {
    name: 'cards-0-Desktop',
    figmaUrl: 'https://www.figma.com/design/[fileId]/[fileName]?node-id=1-2',
    format: 'png',
    scale: 1,
  },
  {
    name: 'cards-0-Mobile',
    figmaUrl: 'https://www.figma.com/design/[fileId]/[fileName]?node-id=1-3',
    format: 'png',
    scale: 2,
  },
];

2. Download Images from Figma

npm run test:visual:figma

This command will:

  • Scan all block folders for config.js files
  • Parse Figma URLs and authenticate with Figma API
  • Download images from Figma
  • Save them to the appropriate snapshot directories

Figma Configuration Options

Property Type Description
name string Snapshot filename (e.g., 'cards-0-Desktop')
figmaUrl string Full Figma URL with node-id
format string Image format: 'png', 'jpg', 'svg', or 'pdf'
scale number Scale factor: 1, 2, or 4

Benefits of Figma Integration

  • Single Source of Truth: Designs live in Figma, tests automatically sync
  • Automated Baseline Generation: No manual screenshot capture needed
  • Easy Design Updates: Re-download when designs change with one command
  • Designer-Developer Collaboration: Direct design-to-test workflow
  • Time Savings: 90% faster baseline creation compared to manual screenshots

Test Sensitivity Settings

Visual comparison uses strict settings which can be changed based on the needs of the project for accurate detection:

expect(screenshot).toMatchSnapshot(screenshotName, {
  maxDiffPixels: 50,         // Maximum pixel differences
  threshold: 0.05,           // 5% color difference tolerance
  maxDiffPixelRatio: 0.005,  // 0.5% of total pixels tolerance
});

Usage

Workflow Options

The visual testing framework supports two main workflows for creating and managing test baselines:

Option 1: Figma-Based Workflow (Recommended)

Best for: Teams using Figma for design, automated baseline management, design-to-development workflow

  1. Designer creates/updates component mockup in Figma
  2. Developer creates block folder: tools/visual-tests/blocks/my-block/
  3. Add Figma configuration in config.js with Figma URLs
  4. Run npm run test:visual:figma to download baselines automatically
  5. Run npm run test:visual:generate to create test files
  6. Run npm run test:visual:block -- tools/visual-tests/blocks/my-block to test
  7. When designs update, re-run npm run test:visual:figma

Time saved: ~90% compared to manual screenshot management

Option 2: Manual Baseline Management

Best for: Teams without Figma, custom baseline requirements

  1. Generate test files: npm run test:visual:generate
  2. Run tests initially: npm run test:visual:update to create baselines
  3. Manually adjust baseline screenshots in block-specific snapshot directories
  4. Run tests: npm run test:visual
  5. Update baselines when needed: npm run test:visual:update

Sidekick Library Usage

Visual tests are automatically configured when you navigate to the Sidekick Library page.

1. Navigate to the sidekick library URL

By default the sidekick library is available at:

http://localhost:3000/tools/sidekick/library.html?plugin=blocks

2. Run Test for a Block

  • Open the block from the sidebar and we should see the run test and toggle overlay button in the top bar.
  • Click on the Run Test to run the test for the block and its variations.
  • Baseline screenshots are stored in block-specific directories: tools/visual-tests/blocks/[block-name]/[block-name].spec.js-snapshots/
  • Snapshots follow the naming convention: block-name-0-Desktop.png, block-name-0-Mobile.png, block-name-0-Tablet.png, block-name-0-Large.png (note the PascalCase viewport names)

3. Test Results

After running the test, we should see the test results report generate in the window. Report should have the screenshots and a video of the tests and the differences if any for all the variations in the configured viewports.

4. Toggle Overlay

Click on the Toggle Overlay button to toggle the overlay on the page. This will show the baseline screenshots and the test results report in the overlay.

Configuring Image Directory

The image directory for the toggle overlay can be configured in test-config/config.js:

export const OVERLAY = {
  imageRoot: '/tools/visual-tests/blocks',
};

The imageRoot property specifies the base path where the overlay will look for baseline screenshots. The overlay automatically looks in block-specific directories: /tools/visual-tests/blocks/{component}/{component}.spec.js-snapshots/ and expects images to follow the naming convention: {component}-{variation}-{viewport}.png (e.g., cards-0-Desktop.png).

Available Commands

The visual test system provides several npm commands for different testing scenarios:

1. Figma Integration

npm run test:visual:figma

Downloads images from Figma based on block configurations. This command:

  • Scans all block folders for config.js files
  • Reads FIGMA_CONFIG arrays
  • Authenticates with Figma API using your access token
  • Downloads images and saves them to snapshot directories
  • Automatically organizes files by block

2. Basic Visual Testing

npm run test:visual

Runs all visual regression tests using Playwright. This command executes the complete test suite across all blocks and viewports, and generates comparison reports.

3. Interactive Visual Testing

npm run test:visual:ui

Launches the Playwright UI mode for interactive testing. This provides a graphical interface where you can:

  • Run tests individually or in groups
  • View test results in real-time
  • Debug failed tests with step-by-step execution
  • Inspect screenshots and compare differences

4. Test All Blocks

npm run test:visual:blocks

Runs visual tests for all blocks. Each block is tested independently in its own test file.

5. Test Specific Block

npm run test:visual:block -- tools/visual-tests/blocks/cards

Runs visual tests for a specific block only. This is useful for:

  • Testing individual components during development
  • Faster feedback loops (20 seconds vs 2 minutes)
  • Focusing on blocks that have been modified
  • Reducing test execution time for targeted testing

6. Update All Baseline Screenshots

npm run test:visual:update

Updates all baseline screenshots with current test results. Use this command when you've made intentional visual changes and want to establish new baselines for future comparisons.

7. Update Specific Block Baselines

npm run test:visual:block:update -- tools/visual-tests/blocks/cards

Updates baseline screenshots for a specific block only. Similar to the global update command, but only affects the specified block's baselines.

8. View Test Reports

npm run test:visual:report

Opens the Playwright HTML report in your default browser. The report includes:

  • Test execution summary and statistics
  • Side-by-side screenshot comparisons
  • Detailed failure information
  • Performance metrics and timing data

9. Generate Visual Tests

npm run test:visual:generate

Automatically discovers all blocks in your AEM Sidekick Library and generates Playwright test specifications. This command:

  • Scans the Sidekick Library for all available blocks
  • Creates individual test files for each block
  • Creates block-specific directories
  • Sets up viewport configurations
  • Prepares test URLs and selectors

10. Start Visual Test Server

npm run test:visual:server

Starts the visual test server on port 3001 (or the next available port). This server provides:

  • Health check endpoints for CI/CD integration
  • Test report serving capabilities
  • Cross-origin request handling
  • Status monitoring for the Sidekick Library integration

Troubleshooting

General Issues

  • Run test button not visible: Make sure to add code snippet in scripts.js file.
  • Tests failing with timeout error: Make sure to add the right path for your blocks templates in test-config/config.js file.
  • Server not starting: Check if port 3001 is available or if another instance is running. The server will automatically try the next available port.
  • Tests failing: Ensure AEM server is running on localhost:3000
  • Baseline mismatches: Review intentional changes and update baselines with npm run test:visual:update or npm run test:visual:block:update
  • Block not found: Verify block exists in Sidekick Library and is accessible

Figma Integration Issues

  • Figma token required error: Create a .env file with FIGMA_ACCESS_TOKEN=your_token. Get your token from Figma → Settings → Account → Personal Access Tokens.
  • Figma API request failed (403): Check that your token is valid, not expired, and has read access to the file. Verify the Figma file is not private.
  • Invalid Figma URL: Ensure the URL includes both file ID and node-id parameter. Format: https://www.figma.com/design/[fileId]/[fileName]?node-id=1-2
  • Images not downloading: Verify your internet connection and that Figma's API is accessible. Check the console output for specific error messages.
  • Wrong images downloaded: Double-check the node-id in your Figma URL. The node-id should point to the specific frame or component you want to export.

Block-Specific Issues

  • Snapshots in wrong location: Verify snapshots are in tools/visual-tests/blocks/[block-name]/[block-name].spec.js-snapshots/
  • Test file not generated: Run npm run test:visual:generate and check that the block appears in the Sidekick Library.
  • Naming convention errors: Ensure snapshot names use PascalCase for viewports (Desktop, Mobile, Tablet, Large) not lowercase.

Pre-commit Hook Setup

The project includes a pre-commit hook that automatically runs visual tests before each commit to ensure code quality and prevent visual regressions from being committed.

Installation

The pre-commit hook is automatically installed when you run:

npm install

This works because the package.json includes a prepare script that runs husky install.

Configuration

You can control the pre-commit hook behavior using environment variables:

  • Disable Visual Tests: Create a .env file in your project root and add VISUAL_TEST=false
  • Enable Visual Tests (default): Either don't create a .env file or set VISUAL_TEST=true

How It Works

  • The hook runs visual tests before each commit
  • If tests fail, the commit is blocked
  • The hook includes automatic retry logic (up to 2 attempts)
  • If tests pass, the commit proceeds normally
  • If tests fail after retries, you must fix the issues before committing

Manual Override

To bypass the pre-commit hook for a specific commit (not recommended for production code):

git commit --no-verify -m "Your commit message"

Hook Location

The pre-commit hook is located at .husky/pre-commit and contains the following logic:

  • Checks for VISUAL_TEST=false in .env file
  • Runs npm run test:visual with retry logic
  • Automatically stages files if tests pass
  • Blocks commit if tests fail after retries
