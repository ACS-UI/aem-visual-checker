MCP server · AEM Edge Delivery Services

pixel-guard

Every block variation in your Sidekick Library, rendered at four viewports and diffed pixel-by-pixel against a baseline you've committed — so a CSS change to one block can't quietly break another. An agent can drive the whole loop through MCP tools, or you can run the exact same Playwright suite yourself, by hand, any time.

Overview

What this is

An MCP server that scaffolds, generates, runs, and helps fix a Playwright-based visual regression suite for AEM Edge Delivery Services (EDS) blocks. It doesn't just execute tests — it installs the environment into your project, keeps the tests in sync with your Sidekick Library, runs them, and hands back enough detail to fix or accept a failure without guessing.

There are two ways to use it, and this page covers both:

  • Through an agent — Claude Code (or any MCP-compatible client) calls the tools under Tools to install, generate, run, and fix the suite for you, following the loop under Workflow.
  • Directly — everything those tools do is really just orchestrating an ordinary Playwright project and a Docker container. The visual test suite below documents exactly how a test runs and every command you can run yourself, with no agent involved.

Install

Setting up pixel-guard itself

Prerequisites

Node.js Docker

The Playwright runner always executes inside a Docker container, matching the exact image CI uses — this keeps font rendering pixel-identical between every machine and CI, so there's no separate local-CLI path to fall out of sync.

npm install

Connect it as an MCP server

Via Claude Code's .mcp.json (or the equivalent config in any other MCP-compatible client):

{
  "mcpServers": {
    "pixel-guard": {
      "command": "npx",
      "args": ["tsx", "/absolute/path/to/pixel-guard/src/index.ts"]
    }
  }
}

Pointing it at your project

Every tool accepts an optional projectDir — the absolute path to the AEM project you want to test. In practice you rarely need to set it: when Claude Code is launched from inside that project, it's picked up automatically. Only pass it explicitly if you're calling a tool from somewhere with no notion of "the current project."

It asks before it commits to something. These tools won't silently make a judgment call for you — accepting a new visual baseline, adding a GitHub Actions workflow. Whenever a decision like that comes up, the tool's response tells your agent to check with you first, then call the right follow-up tool with your answer.

Installing into a target AEM project

This is what aemVisualTestInstall does. It first checks that the target looks like an AEM EDS project — it must have blocks/, scripts/aem.js, package.json, and head.html — and that Docker is installed. Then it:

  1. Copies tools/visual-tests/, tools/sidekick/, tools/visual-overlay/, .dockerignore, and .env.example into the project.
  2. Merges the required npm scripts and dependencies into the project's package.json, and appends the required lines to .gitignore / .hlxignore.
  3. Wires the Sidekick Library loader into scripts/scripts.js.
  4. Runs npm install and generates the initial visual tests from the Sidekick Library.
  5. Installs a Claude Code skill at .claude/skills/pixel-guard-visual-test-fix/.

Re-running it force-overwrites tools/ — safe to use to pick up updates (e.g. a newer Playwright JSON-reporter config).

Tools

MCP tool reference

Five tools. See AGENTS.md in the repo for the exact input schema of each one.

aemVisualTestInstall

Installs/scaffolds the environment (see Install above). On success, tells the agent to ask the user about a GitHub Actions workflow and/or a Husky pre-commit hook, and to call installVisualTestAutomation if wanted.

Input: projectDir?

Set up visual regression testing for this AEM project.

generateVisualTests

Regenerates Playwright specs from the Sidekick Library's current blocks and variations. Assumes the environment is already installed.

Input: projectDir?

I added a new block variation, regenerate the visual tests.

runVisualTestsmode: quick / diagnose / interactive

Runs the suite (all, or one block via blockName) and lists every block/viewport test as pass or fail, not just an aggregate. quick (default) is just that breakdown; diagnose adds each failure's clean error message and the file path to its Playwright screenshot-diff image; interactive adds the same plus a reminder to confirm with the user before attempting a fix.

Input: blockName?, projectDir?, mode? (default "quick")

Run the visual tests and show me why they're failing.Run visual tests for the Columns block.

updateVisualSnapshots

Accepts the current render as the new committed baseline (all, or one block). Only for intentional visual changes — it overwrites the source of truth.

Input: blockName?, projectDir?

Update the visual snapshots, the Columns redesign is intentional.

installVisualTestAutomation

Sets up a GitHub Actions workflow and/or a Husky pre-commit hook in an already-installed project (see Continuous integration below for what each one actually does). Takes explicit flags rather than asking itself — the agent asks the user first, then calls this.

Input: githubWorkflow? (default false), huskyPreCommitHook? (default false), projectDir?

Add the GitHub Actions workflow and the pre-commit hook.

Workflow

Catching a regression

How the tools above chain into a loop an agent runs end to end — also exactly what the pixel-guard-visual-test-fix skill encodes.

  1. Regenerate if blocks changed.

    If a block or Sidekick Library variation changed, call generateVisualTests first so every current variation has a test.

  2. Run and diagnose.

    Call runVisualTests with mode: "diagnose". Read the diff image for each failure.

  3. Decide: regression or intentional.

    Regression → fix the block's code and re-run for that block until it passes. Intentional → confirm with the user, then updateVisualSnapshots to accept the new baseline.

  4. Confirm.

    Re-run the full suite and summarize which blocks were fixed vs. which baselines were intentionally updated.

Visual test suite

How the tests actually work

Everything above is really just an agent orchestrating this suite for you. Once installed, it's an ordinary Playwright project living in tools/visual-tests/ — every command below works exactly the same run by hand, no agent or MCP involved.

How it fits together

tools/sidekick/ hosts the Sidekick Library UI that renders each block/variation in an iframe — the same view authors use. tools/visual-tests/ holds the generated specs, the shared config, and the committed baseline PNGs. tools/visual-overlay/ adds a "Toggle Overlay" button for eyeballing drift directly in the library. Tests run against your local AEM dev server (aem up, http://localhost:3000).

How one test runs

Each generated spec does the following, once per viewport:

  1. Navigate to /tools/sidekick/library.html?plugin=blocks&path=<template>&index=<variation>&vtest=true — the vtest=true flag strips the library's chrome so the block renders at full width.
  2. Wait for the sidekick-library component, then reach into its shadow DOM/iframe to find the block-renderer iframe and the rendered block element.
  3. Wait briefly for layout to settle, force overflow: visible / max-height: none so nothing is clipped, then resize the viewport to the block's actual bounding-box height.
  4. Take a clipped screenshot of just the block and compare it against the committed snapshot.

Baselines: rendered screenshot vs. Figma design

A snapshot in blocks/<name>/<name>.spec.js-snapshots/ gets there one of two ways: run npm run test:visual:update once, review the output, and commit it as the source of truth — or export it straight from a Figma design (see Configuration for the exact setup). Either way, Playwright treats it the same: the thing already on disk is the truth to diff against.

Regenerating specs

Specs aren't hand-written. npm run test:visual:generate launches headless Chromium inside the same Docker container used for tests, opens the Sidekick Library, and walks its shadow DOM to enumerate every block and variation registered in it — then groups them by block name and writes one blocks/<block>/<block>.spec.js file with a test per variation × viewport. Re-run it whenever a block or its variations change so the specs stay in sync; it's a code generator, so edit the library content or the generator, never a generated spec file by hand.

Authoring-time helpers

  • "Run Test" button — injected into the Sidekick Library iframe, it adds a server-status indicator and a button next to the block toolbar so an author can trigger the suite for the block they're viewing without leaving the browser, then see the HTML report in a modal.
  • "Toggle Overlay" button — ghosts the matching baseline image (picked by current viewport) over the live block at an adjustable opacity, for eyeballing drift against the design directly in the library.

The local test server

npm run test:visual:server (or npm start, which runs it alongside aem up) starts an Express app on port 3001+ (auto-increments if busy, writes the chosen port to port.txt):

  • GET /api/health — used to detect whether the server is already running.
  • POST /api/run-visual-test — runs the suite for the requested block (name validated against ^[a-z0-9-]+$).
  • GET /playwright-report/* — serves the last HTML report, so the "Run Test" button can show results in an iframe.

Only needed for the in-browser "Run Test" button — not required in CI.

Running it yourself

ScriptWhat it does
npm startBoots the AEM dev server and the visual-test server together.
npm run test:visual:buildBuilds the Playwright Docker image (first run, or after the Dockerfile changes).
npm run test:visualRuns the full suite inside Docker.
npm run test:visual:updateSame, but overwrites baselines with the result (--update-snapshots).
npm run test:visual:block -- <path>Runs (or, with :update, updates) just the spec at <path>, e.g. tools/visual-tests/blocks/cards.
npm run test:visual:generateRegenerates specs from the Sidekick Library.
npm run test:visual:figmaDownloads Figma frames as baselines (runs on the host, no Docker).
npm run test:visual:reportOpens the last Playwright HTML report.
npm run test:visual:serverStarts just the Express server used by the in-browser "Run Test" button.

Playwright and its snapshots only ever run inside Docker — this keeps font rendering pixel-identical between every machine and CI, so there's no separate local-CLI path to fall out of sync. A typical local session:

# one-time
npm i

# start the AEM dev server (the container's BASE_URL target)
npm start

# in another terminal
npm run test:visual:build   # build the image
npm run test:visual         # run the suite in the container
npm run test:visual:update  # ...or run with --update-snapshots

# open the last HTML report
npm run test:visual:report

To scope a run to one block, append its spec path after --: npm run test:visual:block -- tools/visual-tests/blocks/cards (the same trick works with test:visual:update).

Adding a new block or variation

  1. Make sure the block and its variations are registered in the Sidekick Library.
  2. Run npm run test:visual:generate to (re)generate blocks/<block>/<block>.spec.js.
  3. Either run npm run test:visual:update and review/commit the generated PNGs, or add a config.js with FIGMA_CONFIG and run npm run test:visual:figma.
  4. Run npm run test:visual and confirm it's green before committing the snapshots.

Continuous integration

Installed by installVisualTestAutomation (githubWorkflow: true) as .github/workflows/visual-tests.yaml. On every pull request targeting main or any visual-test* branch, it:

  1. Checks out the repo and runs inside the exact same mcr.microsoft.com/playwright:v1.53.1-jammy image used for local Docker runs — no browser install step, baselines stay pixel-identical between CI and local.
  2. Runs npm ci, installs @adobe/aem-cli globally (the Playwright config drives aem up as the local dev server), then runs the suite with --reporter=html,json.
  3. Uploads the HTML report as an artifact always (7-day retention); on failure only, also uploads test-results/ with the failure screenshots/traces (3-day retention).
  4. Posts, or updates, a single PR comment: pass/fail counts, badges, a collapsible per-test table (failures first), and a link to the report.
  5. Fails the job afterward if any test failed — deliberately after the report/comment steps, so those artifacts are always available even on a red run.

The pre-commit hook

Installed by installVisualTestAutomation (huskyPreCommitHook: true) at .husky/pre-commit:

  • Skipped entirely if .env has VISUAL_TEST=false.
  • Otherwise requires Docker to be installed and running, then runs npm run test:visual, retrying once (2 seconds apart) before giving up.
  • On success, stages any changed files (git add .) and lets the commit through; if it's still failing after both attempts, it blocks the commit.

Figma-sourced baselines

Add a config.js next to a block's spec to pull its baseline from a Figma export instead of a Playwright-rendered screenshot:

// tools/visual-tests/blocks/cards/config.js
export const FIGMA_CONFIG = [
  {
    name: 'cards-0-Desktop',
    figmaUrl: 'https://www.figma.com/design/<fileId>/<fileName>?node-id=1-2',
    format: 'png',
    scale: 1,
  },
];

Then run npm run test:visual:figma. Needs FIGMA_ACCESS_TOKEN in the environment/.env and a node-id in the URL.

Environment variables

VariableNotes
FIGMA_ACCESS_TOKENPersonal access token, required for npm run test:visual:figma. Get one at Figma → Settings → Account → Personal Access Tokens.
PORTVisual-test Express server port, default 3001, auto-increments if busy.
VISUAL_TESTSet to false in .env to skip the pre-commit hook.
CLAUDE_PROJECT_DIRSet automatically by Claude Code — this is how pixel-guard finds your project without you passing projectDir by hand.

Never commit .env — it's in .gitignore by default in an installed project.

Troubleshooting

Common snags

Setup

  • Docker not installed/running — required for every test command and the pre-commit hook; there's no local-CLI fallback. macOS: brew install --cask docker. Windows: winget install Docker.DockerDesktop.
  • "missing blocks/ folder" / "missing scripts/aem.js" — aemVisualTestInstall refused because the target doesn't look like an AEM EDS project. It checks for blocks/, scripts/aem.js, package.json, and head.html.
  • Sidekick Library not found / test generation fails — the library needs to exist first: a /tools/sidekick mountpoint with a blocks subfolder and a library sheet pointing at each block's variations document. See aem.live/docs/sidekick-library.

Running & CI

  • diagnose/interactive falls back to coarse pass/fail — the per-test breakdown and diff-image paths need Playwright's JSON reporter in tools/visual-tests/playwright.config.ts. Projects installed before it was added won't have it — re-run aemVisualTestInstall (it force-overwrites tools/).
  • Local pass, CI fail (or vice versa) — make sure you're actually running inside Docker (npm run test:visual); a bare non-Docker run isn't expected to match font rendering.
  • Figma download fails — check FIGMA_ACCESS_TOKEN is set and the figmaUrl contains a node-id query param.
  • "Run Test" button greyed out in the library — the visual-test Express server isn't running; start it with npm run test:visual:server or npm start.
  • Tests time out waiting for sidekick-library/iframe — confirm aem up is serving on http://localhost:3000 and the block/variation path used in the spec still exists in the library.
