Before you start

Prerequisites

This guide assumes the block you're touching already works and already has baseline snapshots committed on main. If it doesn't exist yet, generate baselines first — this doc only covers changing something that already has them.

  • Docker installed and running. This is what makes your snapshots match CI pixel-for-pixel.
  • Node.js and Git installed. Any recent LTS Node version works.
  • Repo cloned locally, with the block's existing code and baseline images already on main.

One-time setup

Install

Same two tools on both platforms — Docker Desktop and Node.js. Windows needs WSL2 underneath Docker; macOS doesn't.

macOS

  1. Install Docker Desktop for Mac from docker.com and open it once so it's running.
  2. Install Node.js (LTS) from nodejs.org, if you don't already have it.
  3. Clone the repo and cd into it.

Windows

  1. Open PowerShell as Administrator and run wsl --install, then restart if prompted.
  2. Install Docker Desktop for Windows from docker.com — keep "Use the WSL 2 based engine" checked (default) and open it once.
  3. Install Node.js (LTS) from nodejs.org.
  4. Clone the repo and cd into it.

Then, on either platform:

npm install
cd tools/visual-tests
npm install
cd ../..

That's it — no extra config. A commit hook that runs your visual tests automatically gets wired up as part of npm install.

Everyday workflow

The loop

This is the cycle you'll repeat for every story that touches a block's look.

1

Pick up the story

Pull the latest main and branch off it as usual.

2

Start the dev server

Leave this running in its own terminal for the rest of your session:

aem up
3

Make your change

Edit the block's JS/CSS the way you normally would, and eyeball it in the browser at localhost:3000.

4

Run the full test suite

With Docker Desktop and aem up both running:

npm run test:visual:docker

Check the results. Only the block you changed should fail. Everything else should stay green.

If a block you didn't touch also turns red, stop — your change has a side effect somewhere else. Fix that before continuing.
5

Update that block's baseline

Once you're happy the new look is correct, regenerate snapshots for just that block — never leave the block name off:

npm run test:visual:docker:block -- tools/visual-tests/blocks/<your-block> --update-snapshots
Scoping to your block matters — an unscoped update silently accepts every other diff too, including real regressions.
6

Commit and push

Stage your code and the updated .png baselines, then commit as usual. A pre-commit hook reruns the visual tests for you in Docker — there's no local fallback, so Docker Desktop needs to be running — and blocks the commit if anything still fails, so a broken snapshot can't sneak through.

Push and open your PR.

7

CI has the final word

GitHub Actions reruns the full suite in the same Docker image and posts a pass/fail table straight on your PR, with a link to the full report.

When things look wrong

Troubleshooting

Every block is failing, not just mine

Usually means aem up or Docker isn't actually running, or your local main is stale. Confirm both are up, then pull latest main and try again.

My baseline update touched blocks I didn't change

You ran an unscoped update. Restore the ones you didn't mean to touch with git checkout -- tools/visual-tests/blocks/<other-block>, then redo step 5 scoped to your block only.

I need to bypass the commit hook just this once

Set VISUAL_TEST=false in your local .env — but only if you've already verified the change visually another way, and never commit that setting.

Questions about a specific failure? Open the HTML report first (npm run test:visual:report) — it shows the baseline, your result, and the pixel diff side by side.
